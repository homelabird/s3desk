# S3Desk UI/UX 최적화 및 개선 리포트

Date: 2026-07-31

## 목적

이 리포트는 현재 `s3desk` 프론트엔드에서

- 최적화가 필요한 코드
- 개선이 필요한 디자인
- 실제로 어떤 방식으로 개선하는 것이 좋은지

를 현재 워크트리와 현재 시각 스냅샷 기준으로 정리한 실행용 문서다.

## 요약

현재 `s3desk`는 기본 색 대비나 표면 구분보다 더 상위 단계의 문제가 남아 있다.

- 화면 문제: 정보 위계가 약하고, 상단 조작부가 본문보다 강하며, 모바일에서 chrome이 과하다.
- 코드 문제: 레이아웃 분기와 액션 조합이 한 컴포넌트에 몰려 있고, 데스크톱/모바일 렌더링이 중복되며, CSS가 현실 데이터보다 짧은 텍스트를 가정한다.

즉, 지금 필요한 것은 색상 재조정이 아니라 다음 세 가지다.

1. 화면의 주연을 컨트롤에서 콘텐츠로 되돌리기
2. 데이터 길이에 강한 레이아웃으로 바꾸기
3. 복잡한 뷰 컴포넌트의 책임을 줄여 수정 비용을 낮추기

## 1. 최우선 최적화 대상 코드

### 1-1. `ObjectsToolbar.tsx`

- 파일: `frontend/src/pages/objects/ObjectsToolbar.tsx`
- 현재 문제:
  - 데스크톱과 모바일 렌더링이 한 파일 안에서 크게 갈라진다.
  - `upload`, `download`, `delete`, `details`, `more` 같은 액션 조합이 조건 분기 안에 반복된다.
  - 툴바가 단순 표시 계층이 아니라 정책, 상태, 액션 조합, 반응형 분기까지 모두 떠안고 있다.
- 왜 최적화 대상인가:
  - 디자인 수정이 필요할 때마다 이 파일의 분기 구조까지 함께 건드려야 한다.
  - “레이아웃 변경”과 “행동 규칙 변경”이 분리되지 않아 수정 비용이 크다.
  - 같은 액션을 데스크톱/모바일에서 다른 방식으로 유지해야 해서 회귀 위험이 높다.
- 권장 개선 방식:
  - 액션 계산과 액션 렌더링을 분리한다.
  - 먼저 공통 액션 목록을 만들고, 데스크톱/모바일은 그 목록을 어떻게 배치할지만 결정하게 만든다.
  - `ObjectsToolbarDesktop`, `ObjectsToolbarMobile` 같은 표시 전용 컴포넌트로 나누되, 액션 생성 로직은 하나로 유지한다.
- 기대 효과:
  - 디자인 변경이 쉬워진다.
  - 액션 우선순위 조정이 쉬워진다.
  - 반응형 레이아웃 변경이 구조 변경으로 번지지 않는다.

### 1-2. `ObjectsGlobalSearchResults.tsx`

- 파일: `frontend/src/pages/objects/ObjectsGlobalSearchResults.tsx`
- 현재 문제:
  - 모바일 카드형 결과와 데스크톱 테이블형 결과를 한 컴포넌트에서 같이 다룬다.
  - 액션 버튼 묶음이 `compact` 플래그 하나로 두 역할을 동시에 수행한다.
  - 긴 key 데이터에서 테이블 구조가 시각적으로 불안정하다.
- 왜 최적화 대상인가:
  - 검색 결과는 데이터량과 key 길이의 영향이 큰 화면인데, 현재 구조는 “화면 모드”와 “행 액션 배치”가 너무 강하게 묶여 있다.
  - 테이블/카드 레이아웃을 각각 튜닝하기 어렵다.
- 권장 개선 방식:
  - `SearchResultsTable`, `SearchResultsCards`, `SearchResultActions`로 나눈다.
  - `compact` boolean 대신 명시적인 variant를 사용한다. 예: `variant: 'table' | 'card'`.
  - 데스크톱은 “key 우선”, 모바일은 “행동 우선”으로 별도 레이아웃을 허용한다.
- 기대 효과:
  - 긴 key 대응이 쉬워진다.
  - 테이블 액션 폭 축소, 행 높이 조정, 열 우선순위 조정이 단순해진다.
  - 검색 결과 디자인 실험이 다른 화면에 덜 영향을 준다.

### 1-3. `ObjectsSearch.module.css`

- 파일: `frontend/src/pages/objects/ObjectsSearch.module.css`
- 현재 문제:
  - `Last modified`, `Actions` 영역에 고정폭 성격이 강하다.
  - 현실적인 S3 key 길이보다 짧은 데이터를 기준으로 설계되어 있다.
  - 검색 입력/필터/결과가 한 파일에서 너무 많은 역할을 공유한다.
- 왜 최적화 대상인가:
  - CSS만 조금 바꿔도 검색 결과 전체가 쉽게 흔들린다.
  - 레이아웃 토큰이 “보기 좋은 상태”에는 맞지만 “문제 데이터”에는 덜 강하다.
- 권장 개선 방식:
  - 테이블 관련 토큰과 검색 입력 관련 토큰을 분리한다.
  - `Actions` 컬럼은 우선 줄이고, `Key` 컬럼은 더 큰 최소 여유를 갖게 한다.
  - 긴 key는 줄바꿈을 허용하되, 다른 열은 줄 수를 제한하는 방향으로 재설계한다.
- 기대 효과:
  - 실제 운영 데이터에서 검색 결과가 덜 깨진다.
  - CSS 조정 범위가 줄어든다.

### 1-4. `FullAppInner.module.css`

- 파일: `frontend/src/FullAppInner.module.css`
- 현재 문제:
  - 전역 헤더가 모바일에서도 강한 존재감을 유지한다.
  - 헤더, 프로필 셀렉트, 전역 액션, sticky banner, 본문이 모두 상단 공간을 나눠 쓴다.
- 왜 최적화 대상인가:
  - 페이지별 개선을 해도 전역 shell의 높이와 간격 정책이 병목이 된다.
  - 모바일에서 “앱 chrome”과 “실제 작업”의 균형이 깨지기 쉽다.
- 권장 개선 방식:
  - 모바일에서는 헤더 높이와 내부 간격을 더 공격적으로 줄인다.
  - `profile row`와 `global actions`를 항상 같은 위계로 유지하지 말고, 페이지 맥락에 따라 압축 가능한 구조로 바꾼다.
  - 페이지별 본문 시작 위치를 더 빨리 가져오도록 shell padding 정책을 낮춘다.
- 기대 효과:
  - 모든 모바일 페이지의 첫 화면 효율이 좋아진다.
  - `Uploads`, `Objects`, `Settings`, `Transfers` 개선이 동시에 쉬워진다.

### 1-5. `UploadsPage.module.css`

- 파일: `frontend/src/pages/UploadsPage.module.css`
- 현재 문제:
  - 카드와 섹션 구조는 안정적이지만, 첫 액션보다 소개/카드 헤더가 먼저 보인다.
  - 정보 카드, 선택 카드, 요약 카드가 모두 비슷한 무게를 갖는다.
- 왜 최적화 대상인가:
  - 업로드는 “즉시 행동”이 중요한 화면인데, 현재 구조는 설명을 먼저 읽게 만든다.
- 권장 개선 방식:
  - 첫 화면에서 `Add from device…`를 더 위로 끌어올린다.
  - 요약 카드와 설명 문장을 기본 흐름에서 약화하고, 실제 업로드 시작 액션을 강화한다.
  - `Target & source`와 `Selection` 사이 우선순위를 다시 나눈다.
- 기대 효과:
  - 모바일 업로드 시작 시간이 줄어든다.
  - 첫 화면의 의사결정 부담이 줄어든다.

## 2. 개선해야 되는 디자인

### 2-1. Objects 화면

- 가장 큰 문제:
  - 툴바가 파일 목록보다 강하다.
- 사용자가 느끼는 문제:
  - 파일을 보러 왔는데 조작 패널을 먼저 읽게 된다.
  - 리스트의 정보 밀도보다 상단 통제 요소의 밀도가 더 높다.
- 개선 방향:
  - 상단 1차 영역에는 `경로/버킷/핵심 액션`만 남긴다.
  - 검색, 정렬, 보기 전환, 즐겨찾기 같은 보조 제어는 2차 영역으로 내린다.
  - 선택 상태 액션은 기본 툴바가 아니라 selection bar 쪽으로 더 강하게 귀속시킨다.

### 2-2. Global Search 결과 화면

- 가장 큰 문제:
  - 긴 key가 화면 설계의 기준이 아니다.
- 사용자가 느끼는 문제:
  - 가장 중요한 정보인 key를 읽기 어렵다.
  - 액션 버튼 때문에 결과 행이 답답해 보인다.
- 개선 방향:
  - 데스크톱에서는 `Key`를 주열로 보고 나머지를 보조 정보로 약화한다.
  - 액션은 버튼 4개를 그대로 유지하기보다 `Open`만 노출하고 나머지는 메뉴나 아이콘 그룹으로 축약하는 방식을 우선 검토한다.
  - 긴 key는 2줄까지 허용하고 `modified`와 `size`는 compact하게 유지하는 쪽이 낫다.

### 2-3. Mobile Shell

- 가장 큰 문제:
  - 글로벌 chrome이 페이지-local 작업보다 먼저 시선을 가져간다.
- 사용자가 느끼는 문제:
  - 앱 안으로 들어왔는데도 실제 작업 화면보다 앱 프레임을 더 많이 본다.
- 개선 방향:
  - 모바일에서는 헤더를 “브랜드 표시”보다 “상태 전환 도구” 수준으로 축소한다.
  - 페이지 제목, 탭, 액션 버튼이 한꺼번에 첫 화면에 몰리지 않도록 간격과 순서를 조정한다.
  - 본문 첫 카드가 viewport 안에서 더 빨리 시작되게 만든다.

### 2-4. Login 화면

- 가장 큰 문제:
  - 운영용 로그인보다 브랜딩이 더 강하다.
- 사용자가 느끼는 문제:
  - 토큰 입력이라는 단일 과업보다 로고/제품명이 먼저 읽힌다.
- 개선 방향:
  - 모바일에서 로고와 브랜드 영역 높이를 줄인다.
  - 입력 필드, 상태 설명, 로그인 버튼을 하나의 작업 단위로 더 강하게 묶는다.
  - 이 화면은 랜딩 페이지가 아니라 운영 도구 진입점이라는 성격을 반영한다.

### 2-5. Bucket Picker / Settings / Policy / Profile 편집

- 가장 큰 문제:
  - 읽기 쉬워졌지만 여전히 “긴 카드 스택” 느낌이 강하다.
- 사용자가 느끼는 문제:
  - 어디가 추천 경로인지, 어디가 고급 경로인지, 어디가 위험 경로인지 빨리 구분하기 어렵다.
- 개선 방향:
  - 추천 흐름, 고급 흐름, 위험 흐름을 색이 아니라 구조로 먼저 나눈다.
  - 설명은 섹션 상단에 모으고, 실행 버튼은 해당 섹션과 더 밀접하게 배치한다.
  - 상태 badge는 유지하되, 주요 섹션 제목 계층을 더 분명히 한다.

## 3. 어떻게 개선하는 것이 좋은가

### 원칙 1. 큰 구조부터 바꾸고 세부 스타일은 나중에 조정

- 먼저 바꿔야 할 것:
  - 화면 우선순위
  - 영역 분리
  - 데스크톱/모바일 분기 구조
- 나중에 바꿔도 되는 것:
  - 세부 여백 미세 조정
  - 색상 혼합 비율
  - 그림자 강도

### 원칙 2. “더 예쁘게”보다 “더 빨리 읽히게”

- `s3desk`는 마케팅 사이트가 아니라 운영 도구다.
- 따라서 개선 기준은 다음 순서가 맞다.
  1. 지금 해야 할 작업이 바로 보이는가
  2. 긴 데이터가 깨지지 않는가
  3. 위험/추천/보조 경로가 구분되는가
  4. 그 다음이 미관이다

### 원칙 3. 공통 액션과 공통 레이아웃을 먼저 정리

- `ObjectsToolbar.tsx`처럼 공통 액션이 섞인 컴포넌트는 먼저 분리해야 한다.
- 이유:
  - 디자인 개선이 코드 중복 때문에 느려지는 상태를 먼저 끊어야 한다.
  - 구조를 안 바꾸고 CSS만 손보면 같은 문제가 다시 생긴다.

## 4. 권장 실행 순서

### Phase 1. 바로 효과가 큰 작업

- `ObjectsToolbar.tsx` 구조 분리
- `Objects` 상단 영역 2단 재배치
- `ObjectsGlobalSearchResults.tsx`와 `ObjectsSearch.module.css` 재구성

### Phase 2. 모바일 작업성 개선

- `FullAppInner.module.css` 모바일 헤더 압축
- `UploadsPage.module.css` 첫 화면 우선순위 재정렬
- `LoginPage.module.css` / `TokenLoginPanel.module.css` form-first 조정

### Phase 3. 복잡한 시트/모달 정리

- Bucket picker 내부 위계 강화
- Settings / Policy / Profile 편집 흐름을 recommended / advanced / danger 구조로 재배치

## 5. 추천 산출물

이 리포트를 실제 작업으로 옮길 때는 다음 단위가 적당하다.

- 1차 작업:
  - Objects toolbar 리팩터링 + 상단 레이아웃 개선
- 2차 작업:
  - Global search 결과 테이블/카드 개선
- 3차 작업:
  - Mobile shell + uploads/login 개선
- 4차 작업:
  - Bucket picker / settings / policy / profile modal 정리

## 6. 결론

현재 `s3desk`의 다음 단계는 “색상 보정”이 아니라 “운영 도구다운 정보 위계”로 옮겨가는 것이다.

- 코드 측면에서는 `Objects` 관련 뷰 컴포넌트와 shell 레이아웃이 최우선 최적화 대상이다.
- 디자인 측면에서는 상단 조작부 과밀, 긴 데이터에 약한 결과 레이아웃, 모바일 chrome 과다, 단일 과업 화면의 브랜딩 과강조가 핵심 문제다.
- 개선 방식은 CSS 미세 조정보다 구조 분리와 위계 재설계부터 시작하는 편이 맞다.

## 검증 한계

- 현재 환경에서는 `playwright`가 설치되어 있지 않아 브라우저 시각 검증을 재실행하지 못했다.
- 따라서 본 리포트는 현재 체크인된 스냅샷과 현재 소스 기준의 개선 권고 문서다.
